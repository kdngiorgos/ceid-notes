    ## Θέμα 11

    *Αξιοπιστία: δύο ανεξάρτητες λύσεις συμφωνούν · εμπιστοσύνη λύτη: μέτρια*

    Ο κώδικας ως έχει δεν έχει καλά ορισμένη έξοδο: στο `MPI_Allreduce` χρησιμοποιείται `MPI_DOUBLE` για buffers τύπου `int` και το `MPI_INT` στη θέση του τελεστή αντί για έγκυρο `MPI_Op`· επίσης το `printf("%f\n", var3)` τυπώνει `int` ως `double`, που είναι undefined behavior.

    Αν διορθωθούν τα προφανή λάθη σε `MPI_INT, MPI_SUM` και `%d`, τότε:
    - Μετά το `MPI_Reduce`, μόνο στη ρίζα (`rank=0`):
    \[
    var2=\sum_{r=0}^{3}(r-2)=(0+1+2+3)-8=-2.
    \]
    Στους άλλους βαθμίδες το `var2` μένει η αρχική τιμή `rank`, δηλαδή $1,2,3$.
    - Το `MPI_Allreduce` αθροίζει τις τιμές `var2` όλων των βαθμίδων:
    \[
    -2+1+2+3=4.
    \]
    Άρα με τις διορθώσεις, στο `rank=1` τυπώνεται $\boxed{4}$.

    ## Θέμα 12

    *Αξιοπιστία: δύο ανεξάρτητες λύσεις συμφωνούν · εμπιστοσύνη λύτη: υψηλή*

    Μία ισοδύναμη υλοποίηση με MPI κατανέμει τις επαναλήψεις σε συνεχόμενα τμήματα και συγκεντρώνει τα αποτελέσματα σε όλες τις διεργασίες με `MPI_Allgatherv`:
    ```c
    int rank, size;
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);
    MPI_Comm_size(MPI_COMM_WORLD, &size);

    int base = N / size;
    int rem  = N % size;

    int *counts = (int*) malloc(size * sizeof(int));
    int *displs = (int*) malloc(size * sizeof(int));
    int off = 0;
    for (int r = 0; r < size; ++r) {
        counts[r] = base + (r < rem ? 1 : 0);
        displs[r] = off;
        off += counts[r];
    }

    int local_n = counts[rank];
    double *local = (double*) malloc(local_n * sizeof(double));
    for (int j = 0; j < local_n; ++j) {
        int i = displs[rank] + j;
        local[j] = work(i);
    }

    MPI_Allgatherv(local, local_n, MPI_DOUBLE,
                   A, counts, displs, MPI_DOUBLE,
                   MPI_COMM_WORLD);

    free(local);
    free(counts);
    free(displs);
    ```
    Έτσι κάθε διεργασία υπολογίζει το δικό της τμήμα και στο τέλος όλες έχουν το πλήρες διάνυσμα $A$. Αν αρκεί το $A$ μόνο στη ρίζα, χρησιμοποιείται `MPI_Gatherv`.

    ## Θέμα 13

    ## Θέμα 14

    *Αξιοπιστία: δύο ανεξάρτητες λύσεις συμφωνούν · εμπιστοσύνη λύτη: μέτρια*

    Βασικό σφάλμα: το `data` είναι `double*`, αλλά οι εντολές `_mm_load_ps`, `_mm_set1_ps`, `_mm_mul_ps`, `_mm_store_ps` είναι για μονής ακρίβειας `float` (`__m128`, 4 floats). Άρα γίνεται λάθος ερμηνεία μνήμης και ασυμβατότητα τύπων. Επίσης:
    - Το `M_PI` δεν είναι πρότυπο C· χρειάζεται `<math.h>` και κατάλληλη μακροεντολή ή `acos(-1.0)`.
    - Χρειάζονται headers όπως `<omp.h>`, `<immintrin.h>`, `<stdlib.h>`, `<math.h>`.
    - Τα `_mm_load_ps`/`_mm_store_ps` απαιτούν 16-byte ευθυγράμμιση· καλό είναι να χρησιμοποιηθεί `_mm_malloc`/`aligned_alloc` ή `_mm_loadu_ps`/`_mm_storeu_ps` αν δεν είναι εγγυημένη.
    - Αν το `data` μείνει `double`, πρέπει να χρησιμοποιηθούν double intrinsics (`_mm_load_pd`, `_mm_set1_pd`, `_mm_mul_pd`, `_mm_store_pd`) και να προσαρμοστούν τα offsets/πλάτη.

    Μία διόρθωση με `float` είναι:
    ```c
    #include <omp.h>
    #include <immintrin.h>
    #include <stdlib.h>
    #include <math.h>

    int nThreads = 8;
    float *data = (float*) _mm_malloc(32 * sizeof(float), 16);
    for (int i = 0; i < 32; ++i)
        data[i] = (float) drand48();

    #pragma omp parallel num_threads(nThreads)
    {
        int tid = omp_get_thread_num();
        float *myData = data + 4 * tid;

        __m128 c4 = _mm_set1_ps((float) M_PI);
        __m128 r4 = _mm_load_ps(myData);
        __m128 a4 = _mm_mul_ps(c4, _mm_mul_ps(r4, r4));
        _mm_store_ps(myData, a4);
    }
    _mm_free(data);
    ```

    *Αξιοπιστία: δύο ανεξάρτητες λύσεις συμφωνούν · εμπιστοσύνη λύτη: υψηλή*

    Η `__syncthreads()` είναι barrier σε επίπεδο thread block στην CUDA. Συγχρονίζει όλα τα threads του ίδιου block ώστε να φτάσουν στο σημείο αυτό πριν συνεχίσει οποιοδήποτε, και εξασφαλίζει ότι οι εγγραφές στη shared/global μνήμη πριν το barrier είναι ορατές στα threads του block μετά από αυτό. Χρησιμοποιείται κυρίως όταν threads ανταλλάσσουν δεδομένα μέσω shared memory. Δεν συγχρονίζει ολόκληρο το grid.

    ## Θέμα 16

    *Αξιοπιστία: δύο ανεξάρτητες λύσεις συμφωνούν · εμπιστοσύνη λύτη: υψηλή*

    Το kernel εκτελείται με `<<<2, 2>>>`, δηλαδή 2 blocks × 2 threads. Χρησιμοποιεί μόνο το `threadIdx.x`, όχι το `blockIdx.x`. Άρα και τα δύο blocks γράφουν στις ίδιες θέσεις:
    \[
    a[0]=0,\qquad a[1]=2.
    \]
    Οι θέσεις `a[2]` και `a[3]` δεν γράφονται ποτέ. Το `cudaMalloc` δεν μηδενίζει εγγυημένα τη μνήμη, άρα οι τελευταίες δύο τιμές είναι απροσδιόριστες. Η έξοδος θα ξεκινά με `0 2` και μετά θα εκτυπωθούν δύο απροσδιόριστες τιμές· αν κατά τύχη η device μνήμη ήταν μηδενισμένη, θα έβγαινε `0 2 0 0`.

    ## Θέμα 17

    *Αξιοπιστία: δύο ανεξάρτητες λύσεις συμφωνούν · εμπιστοσύνη λύτη: υψηλή*

    Υποθέτοντας ότι υπάρχει device εκδοχή της `work` (π.χ. δηλωμένη ως `__device__`), μία ισοδύναμη CUDA υλοποίηση είναι:
    ```c
    __global__ void init_A(double *A, int N)
    {
        int i = blockIdx.x * blockDim.x + threadIdx.x;
        if (i < N) {
            A[i] = work(i);
        }
    }

    // Host κώδικας:
    double *d_A;
    cudaMalloc((void**) &d_A, N * sizeof(double));

    int threads = 256;
    int blocks  = (N + threads - 1) / threads;
    init_A<<<blocks, threads>>>(d_A, N);

    cudaMemcpy(A, d_A, N * sizeof(double), cudaMemcpyDeviceToHost);
    cudaFree(d_A);
    ```
    Αν το `A` βρίσκεται ήδη στη device μνήμη, παραλείπεται το `cudaMemcpy`. Αν η `work` είναι μόνο host συνάρτηση, δεν μπορεί να κληθεί απευθείας από CUDA kernel· τότε χρειάζεται αντίστοιχη `__device__` υλοποίηση.
