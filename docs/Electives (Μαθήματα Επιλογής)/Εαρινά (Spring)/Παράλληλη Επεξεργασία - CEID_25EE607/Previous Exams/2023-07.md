    ## Θέμα 1°

    *Αξιοπιστία: δύο ανεξάρτητες λύσεις συμφωνούν · εμπιστοσύνη λύτη: υψηλή*

    **1.1**  
    Απάντηση: **b. Την οδηγία `#pragma omp critical`**.  
    Η εισαγωγή σε διπλά διασυνδεδεμένη λίστα απαιτεί πολλαπλές ενημερώσεις δεικτών, οπότε χρειάζεται αμοιβαίος αποκλεισμός σε όλη την κρίσιμη περιοχή. Το `atomic` καλύπτει μόνο απλές, μεμονωμένες ενημερώσεις μνήμης.

    **1.2**  
    Απάντηση: **c. Είτε ως νήματα χρήστη είτε ως νήματα επιπέδου πυρήνα**.  
    Το πρότυπο POSIX Threads καθορίζει το API και όχι την εσωτερική υλοποίηση· μια βιβλιοθήκη Pthreads μπορεί να υλοποιηθεί πάνω από user-level ή kernel-level νήματα.

    **1.3**  
    Απάντηση: **c. firstprivate**.  
    Η `b` είναι `private` στην εξωτερική παράλληλη περιοχή λόγω του `private(b)`. Στο task που δημιουργείται μέσα σε αυτήν, μια μεταβλητή που είναι private στο περιβάλλον δημιουργίας γίνεται από προεπιλογή `firstprivate` μέσα στο task· δηλαδή αντιγράφεται η τιμή της κατά τη δημιουργία του task. (Αν διαβαστεί πριν αρχικοποιηθεί, η τιμή της είναι απροσδιόριστη, αλλά το data-sharing attribute είναι firstprivate.)

    **1.4**  
    Απάντηση: **a. Μπορούν να τερματίσουν σε άλλο νήμα από εκείνο στο οποίο ξεκίνησαν**.

    **1.5**  
    Απάντηση: **c. 10**.  
    Με `num_threads(4)`, για `tid = 0,1,2,3` υπολογίζονται αντίστοιχα:
    \[
    4-0=4,\quad 4-1=3,\quad 4-2=2,\quad 4-3=1.

    4+3+2+1=10.
    \]

    ## Θέμα 2°

    *Αξιοπιστία: δύο ανεξάρτητες λύσεις συμφωνούν · εμπιστοσύνη λύτη: μέτρια*

    **2.1**  
    Με `omp_set_nested(1)` και `omp_set_num_threads(3)`, και υποθέτοντας ότι η υλοποίηση υποστηρίζει και εκτελεί πλήρως το nested parallelism, δημιουργείται εξωτερική ομάδα 3 νημάτων και κάθε εξωτερικό νήμα δημιουργεί εσωτερική ομάδα 3 νημάτων. Άρα θα εκτυπωθούν 9 γραμμές, μία για κάθε ζεύγος
    \[
    (tid1,tid2)\in\{0,1,2\}\times\{0,1,2\},
    \]
    π.χ. `tid1 = 0, tid2 = 0`, …, `tid1 = 2, tid2 = 2`, με τυχαία σειρά λόγω δρομολόγησης. Η `critical` εξασφαλίζει ότι κάθε `printf` εκτελείται ατομικά, χωρίς μπέρδεμα χαρακτήρων. Αν η υλοποίηση δεν υποστηρίζει nested parallelism ή τον σειριοποιήσει, τότε θα εκτυπωθούν μόνο 3 γραμμές με `tid2 = 0`.

    **2.2**  
    **a.** Υπάρχει **data race** στη μεταβλητή `counter`: πολλά νήματα εκτελούν ταυτόχρονα μη ατομική πράξη ανάγνωσης-ενημέρωσης-εγγραφής (`counter += do_work()`). Έτσι μπορεί να χαθούν ενημερώσεις και το τελικό άθροισμα να είναι λάθος/μη ντετερμινιστικό.

    **b.** Μία σωστή διόρθωση είναι να γίνεται ατομική μόνο η ενημέρωση, αφού πρώτα υπολογιστεί το `do_work()`:
    ```c
    void func()
    {
      for (int i = 0; i < 10; i++) {
        double v = do_work();     // το βαρύ έργο γίνεται παράλληλα
        #pragma omp atomic
        counter += v;             // ατομική ενημέρωση του counter
      }
    }
    ```
    Εναλλακτικά, αντί για `atomic` μπορεί να χρησιμοποιηθεί `#pragma omp critical` γύρω από την `counter += v;`. Η λύση με `atomic` είναι προτιμότερη για απλή πρόσθεση, γιατί δεν σειριοποιεί την κλήση της `do_work()`.

    ## Θέμα 3°

    *Αξιοπιστία: δύο ανεξάρτητες λύσεις συμφωνούν · εμπιστοσύνη λύτη: υψηλή*

    **a.** Το `#pragma omp parallel for schedule(dynamic,1)` δημιουργεί παράλληλη ομάδα νημάτων και μοιράζει τις επαναλήψεις του βρόχου σε αυτά. Με `schedule(dynamic,1)` κάθε νήμα παίρνει δυναμικά την επόμενη διαθέσιμη επανάληψη, μία κάθε φορά, όταν τελειώσει την προηγούμενη. Αυτό βοηθά στην εξισορρόπηση φόρτου όταν η `work(i)` έχει μεταβλητό κόστος. Κάθε επανάληψη γράφει σε διαφορετικό στοιχείο `A[i]`, άρα δεν υπάρχει race στα δεδομένα. Στο τέλος της `parallel for` υπάρχει implicit barrier, οπότε όλα τα `A[i]` έχουν αρχικοποιηθεί πριν επιστρέψει η `init`.

    **b.** Υλοποίηση με OpenMP tasks:
    ```c
    void init_v2(double *A, int N)
    {
      #pragma omp parallel
      {
        #pragma omp single
        {
          for (int i = 0; i < N; i++) {
            #pragma omp task firstprivate(i) shared(A)
            {
              A[i] = work(i);
            }
          }
          #pragma omp taskwait
        }
      }
    }
    ```
    Κάθε επανάληψη δημιουργεί ένα task που υπολογίζει ανεξάρτητα το `A[i]`. Το `firstprivate(i)` αποθηκεύει τη σωστή τιμή του `i` για κάθε task, ενώ το `A` είναι κοινό. Το `taskwait` εξασφαλίζει ότι όλα τα tasks ολοκληρώθηκαν πριν βγει το `single`.

    **c.** Υλοποίηση χωρίς `for`, `sections`, `single` ή tasks, με χειροκίνητη κατανομή επαναλήψεων:
    ```c
    #include <omp.h>

    void init_v3(double *A, int N)
    {
      #pragma omp parallel
      {
        int tid = omp_get_thread_num();
        int nt  = omp_get_num_threads();

        for (int i = tid; i < N; i += nt) {
          A[i] = work(i);
        }
      }
    }
    ```
    Κάθε νήμα εκτελεί τις επαναλήψεις \(i=tid, tid+nt, tid+2nt,\ldots\), οπότε όλα τα `i` καλύπτονται ακριβώς μία φορά και δεν χρειάζεται κάποια οδηγία διαμοίρασης έργου.

    ## Θέμα 4°

    ```text
    rank 1: data=2.000000
    rank 2: data=2.000000
    ```

    **b.** Αντικατάσταση της `MPI_Bcast` με point-to-point επικοινωνία (απλή γραμμική εκπομπή από τη ρίζα 2):
    ```c
    int root = 2;

    if (rank == root) {
      for (int dest = 0; dest < size; dest++) {
        if (dest != root) {
    ```

    **c.** Κάθε σωστή εκπομπή χρειάζεται τουλάχιστον \(P-1\) μηνύματα, αφού κάθε μη-ριζική διεργασία πρέπει να λάβει τουλάχιστον ένα μήνυμα.  
    Η βιβλιοθήκη `MPI_Bcast` συνήθως υλοποιείται εσωτερικά με δενδρικό αλγόριθμο: συνολικά χρειάζεται \(P-1\) μηνύματα, αλλά ολοκληρώνεται σε \(O(\log P)\) επικοινωνιακά βήματα/καθυστέρηση.  
    Η απλή point-to-point υλοποίηση της (b), όπου η ρίζα στέλνει διαδοχικά σε όλους, χρειάζεται επίσης \(P-1\) μηνύματα, αλλά σε \(P-1\) διαδοχικά βήματα. Αν η δική μας υλοποίηση γίνει επίσης με δέντρο, τότε θα χρειάζεται πάλι \(P-1\) μηνύματα και \(O(\log P)\) βήματα.
