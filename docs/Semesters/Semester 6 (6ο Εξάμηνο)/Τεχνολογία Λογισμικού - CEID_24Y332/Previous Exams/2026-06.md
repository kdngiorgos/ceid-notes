    # Λύσεις — Τεχνολογία Λογισμικού — Ιούνιος 2026 (Θέμα Α)

    > Μόνο για το Θέμα Α (ερωτήσεις 1–10), δηλαδή το τμήμα που είναι φωτογραφημένο. Οι απαντήσεις είναι με τη σειρά των ερωτήσεων 1 έως 10 και κάθε αιτιολόγηση ακολουθεί την απάντηση της ίδιας ερώτησης. Οι εκφωνήσεις είναι αυτές του [2026-06](2026-06.md).

    - [x] **Το Domain Model δεν περιλαμβάνει λειτουργικότητα (methods)**

    > **Αιτιολόγηση:** Το Domain Model (Μοντέλο Πεδίου) είναι ένα εννοιολογικό μοντέλο ανάλυσης που αναπαριστά τις οντότητες του πραγματικού κόσμου και τις συσχετίσεις τους με ιδιότητες (attributes), χωρίς να περιλαμβάνει μεθόδους/λειτουργίες υλοποίησης λογισμικού (operations/methods), οι οποίες προστίθενται στα διαγράμματα κλάσεων (Design Class Diagrams).

    - [x] **Να καθοριστούν οι ανάγκες των χρηστών**

    > **Αιτιολόγηση:** Η φάση ανάλυσης απαιτήσεων στοχεύει στον εντοπισμό, την κατανόηση, την καταγραφή και την επικύρωση του τι ακριβώς χρειάζονται οι τελικοί χρήστες και τα ενδιαφερόμενα μέρη (stakeholders) από το σύστημα.

    - [x] **Τον αριθμό αντικειμένων που συμμετέχουν σε μια σχέση**

    > **Αιτιολόγηση:** Η πολλαπλότητα (π.χ. $1$, $0..1$, $1..*$, $*$) ορίζει πόσα στιγμιότυπα (instances/αντικείμενα) μιας κλάσης μπορούν ή πρέπει να συνδέονται με ένα στιγμιότυπο της άλλης κλάσης στο πλαίσιο του συσχετισμού.

    - [x] **Διαχείριση εκδόσεων κώδικα**

    > **Αιτιολόγηση:** Το Version Control (όπως το Git) είναι σύστημα παρακολούθησης και διαχείρισης των αλλαγών στον πηγαίο κώδικα και τα αρχεία ενός έργου λογισμικού στην πάροδο του χρόνου.

    - [x] **Τα functional περιγράφουν λειτουργίες, τα non-functional ποιοτικά χαρακτηριστικά**

    > **Αιτιολόγηση:** Οι λειτουργικές απαιτήσεις (Functional Requirements) καθορίζουν τι πρέπει να κάνει το σύστημα (υπηρεσίες, συμπεριφορές, είσοδοι-έξοδοι), ενώ οι μη λειτουργικές απαιτήσεις (Non-Functional Requirements) καθορίζουν περιορισμούς και ποιοτικά χαρακτηριστικά (απόδοση, ασφάλεια, αξιοπιστία, διαθεσιμότητα).

    - [x] **Ο χρόνος απόκρισης είναι < 2 δευτερόλεπτα**

    > **Αιτιολόγηση:** Ο περιορισμός χρόνου απόκρισης ($\text{latency} < 2\text{ sec}$) αποτελεί μη λειτουργική απαίτηση απόδοσης (performance requirement). Τα υπόλοιπα είναι λειτουργικές απαιτήσεις (δράσεις/λειτουργίες του χρήστη και του συστήματος).

    - [x] **Διάγραμμα που δείχνει τις αλληλεπιδράσεις χρηστών με το σύστημα**

    > **Αιτιολόγηση:** Το Use Case Diagram (Διάγραμμα Περιπτώσεων Χρήσης) της UML αναπαριστά οπτικά τους ρόλους των χρηστών (actors) και τις υπηρεσίες/στόχους (use cases) που εκτελούν σε αλληλεπίδραση με το σύστημα.

    - [x] **Χρονική αλληλουχία μηνυμάτων μεταξύ αντικειμένων**

    > **Αιτιολόγηση:** Το Sequence Diagram είναι διάγραμμα αλληλεπίδρασης της UML που παρουσιάζει τα αντικείμενα κατά μήκος γραμμών ζωής (lifelines) και την ακριβή χρονική σειρά ανταλλαγής μηνυμάτων μεταξύ τους.

    - [x] **Να γεφυρώσει use cases με σχεδίαση**

    > **Αιτιολόγηση:** Το Robustness Diagram (Διάγραμμα Ευρωστίας) εισάγει τα στερεότυπα Boundary, Control και Entity για να γεφυρώσει το εννοιολογικό χάσμα ανάμεσα στην περιγραφή των περιπτώσεων χρήσης (ανάλυση) και τον λεπτομερή σχεδιασμό των κλάσεων (design).

    - [x] **Μεταγλώττιση**

    > **Αιτιολόγηση:** Η μεταγλώττιση (compilation) είναι ένα τεχνικό βήμα κατασκευής/μετάφρασης κώδικα εντός της φάσης υλοποίησης, όχι αυτόνομη κύρια φάση του κύκλου ζωής λογισμικού (SDLC: Requirements, Design, Implementation, Testing, Deployment, Maintenance).
